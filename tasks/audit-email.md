# Email/newsletter audit — 2026-10-08 (audit/email branch)

Scope: templates, copy, deliverability. Route logic (`newsletter.ts` double opt-in mechanics) and its tests belong to the api-core agent — untouched. Triggers were traced for verification only; route-logic gaps are listed below for api-core follow-up, not changed here.

Files audited: `api/src/lib/email.ts`, `api/src/routes/introduction.ts`, `api/src/routes/newsletter.ts`, `api/src/routes/auth.ts` (code emails), `api/src/routes/events.ts` (RSVP confirm), `api/src/routes/forms.ts` (submission notify), `api/src/cron.ts` (weekly digest + health alert), `site/src/pages/newsletter.astro`, `docs/` runbooks.

## Errors found

### Critical
1. **Email header logo 404s — every branded email ships a broken image.** `api/src/lib/email.ts` sets `LOGO_URL = https://brimwoodinnovation.com/logo-email.png`, but no `logo-email.png` existed anywhere in the site repo — and `.gitignore` explicitly ignored it (a leftover from the removed `build/` directory; no build step regenerates it). Every one of the 9 branded emails rendered with a broken header image — the single worst brand defect in the email system. (FIXED: rendered a lightweight 560×167 PNG from the kit's supplied `brimwood-logo-reversed.png`, byte-verified kit asset, committed at `site/public/logo-email.png`; removed it from `.gitignore` with an explanatory comment.)

### Major
2. **Weekly digest has no `List-Unsubscribe` header.** The digest is the only bulk marketing email, sent to all active subscribers, but `cron.ts` sends it with no list headers. Gmail/Yahoo bulk-sender rules (Feb 2024, enforcement ramped to permanent rejection through 2025–2026) expect `List-Unsubscribe` on subscribed mail; without it the digest risks Promotions/spam placement. (FIXED: added per-recipient `List-Unsubscribe: <https://…/unsubscribe?email=…&token=…>`.)
3. **RFC 8058 one-click unsubscribe is impossible today.** Full one-click needs `List-Unsubscribe-Post: List-Unsubscribe=One-Click` + an HTTPS endpoint that accepts POST and unsubscribes without further action. The current unsubscribe endpoint is GET-only (and must stay GET-safe for prefetchers/scanners, which must NOT unsubscribe). → **api-core follow-up:** add `POST /api/newsletter/unsubscribe` accepting the same email+token params (or `List-Unsubscribe=One-Click` body), rate-limited, returning 200, performing the same status update; then the digest and newsletter-welcome emails can add the `List-Unsubscribe-Post` header. Also note: Gmail's hard 5k/day bulk threshold doesn't apply at current list size, but these headers are the floor for any subscribed mail.
4. **No SPF/DKIM/DMARC record anywhere in the repo docs.** Memory says Resend domain verification passed and SPF/DKIM/DMARC are verified live (Postmaster Tools), but `docs/` never mentions it — the deliverability posture is invisible to future agents and to anyone onboarding. (FIXED: added `docs/runbooks/email-deliverability.md` recording status, monitoring, and the header policy.)
5. **Newsletter confirm tokens never expire.** `confirm_token` has no expiry; the "link has expired" page only fires for unknown tokens. A leaked/old confirm link confirms a subscription indefinitely. → **api-core follow-up:** add a `confirm_token_expires_at` (or `token_created_at`) column, set a 24–72h expiry on signup, and have the verify handler treat expired tokens as expired (re-send a fresh confirm email on expiry, keep the "resubscribe" page as fallback).

### Minor
6. **Digest personalization was a brittle placeholder dance** (`{{email}}`/`{{token}}` + three chained `.replace()` calls; the third was a dead no-op after the first two mutated the string, and a literal `{{email}}` could leak if a future edit added a second placeholder). (FIXED: digest body is now built per-recipient by `digestBody(site, postItems, lessonItems, unsubUrl)` — no placeholders, `&amp;` in the `href`.)
7. **Digest plain-text body was one line** ("This week at Brimwood — new posts and lessons. Unsubscribe: …") — no titles or links; poor for text-only clients. (FIXED: text digest now lists post/lesson titles + URLs + unsubscribe URL.)
8. **Health-alert subject starts with an emoji** ("⚠ Brimwood health alert — …"). Emojis in subjects raise spam-score risk; internal email, cheap to clean. (FIXED: plain-text subject.)
9. **Email `<html>` had no `lang` and shell had no `<title>`** — HTML email accessibility (screen readers, some clients). (FIXED: `lang="en"` on `shell()` and `page()`; `<title>` in `shell()`.)
10. **Inconsistent name guard in invite-redeem magic-code email** — HTML guards `(name ? … : "")` but the text version interpolates `name` raw. Name is required at signup today so no leak now, but the two sides can drift. (FIXED: text version uses the same guarded form.)
11. **Stale company-level email docs.** `~/workspace/company/email/README.md` still describes the old `brimwood-introduction` live worker, KV storage, and `worker-introduction.js` — and references `../website/logo-email.png`, which didn't exist until this audit. Updating that directory is outside this branch's area; flagged for a docs pass.
12. **Unhandled Resend failures in non-best-effort sends.** `POST /api/newsletter` (confirm email) and `/auth/request-code` `await sendEmail(...)` without try/catch — a Resend outage 500s the request *after* the row is written (subscriber stored as pending, no confirm email sent). Invite-redeem, RSVP, and forms already `.catch()` theirs. → **api-core follow-up:** wrap in try/catch, log to `email_log` as failed, and (for newsletter) still return `ok: true` or requeue — do not leave a pending subscriber with no email.

## What passed
- **No `{{undefined}}` leaks:** all 9 templates render with every variable supplied; text alternatives exist for every HTML email (verified by `api/src/lib/email.render.test.ts`).
- **Brand shell intact:** emerald header `#0C9463`, kit logo, forest footer copy — per the standing email-system record.
- **Double opt-in copy is clear:** newsletter page ("You are only subscribed after you click it"), confirm email ("If you did not request this, just ignore this email"), welcome email with unsubscribe link.
- **Canadian spelling throughout; no US spellings found in copy.** No hype/income language; "Elite by effort, not by background." is the brand standard.
- **Subjects** are consistent and brand-suffixed; **preheaders** present on all shell emails.
- **Trigger trace (verify-only):** intro POST → notify+confirm after D1 insert ✓; newsletter POST → confirm after pending insert ✓; verify GET → welcome + owner notice ✓; auth code → code email ✓ (CODE_TTL 600 matches "expires in 10 minutes" copy); invite redeem → magic code ✓; digest cron → active subscribers only ✓; health alert → INBOX, ≤1/hour ✓; RSVP → confirm, best-effort ✓; forms → notify, best-effort ✓.
- **No secrets in templates** (Resend key only via worker secret); `FROM` uses `introductions@brimwoodinnovation.com` on the verified domain.
- `button()` CTA and `fieldRow()` escape all user input via `esc()`.

## Research notes (C$0, applied where free)
- Gmail/Yahoo bulk-sender rules: SPF + DKIM + DMARC (DMARC ≥ p=none, recommend p=quarantine), `List-Unsubscribe` (RFC 2369) + `List-Unsubscribe-Post` (RFC 8058) on marketing/subscribed mail with an HTTPS POST endpoint (GET must not unsubscribe — prefetchers), visible in-body unsubscribe link (kept), process opt-outs within 48h (instant here), spam complaint rate < 0.3% (target < 0.1%) via Postmaster Tools, double opt-in already in place (single biggest complaint-rate lever), sunset inactives at 90–180 days (future work — list is small), warm new sending identities slowly (Resend shared IP inherits reputation; fine at current volume). Resend free tier: 3k emails/month, 100/day — digest loop already paces at 50/min.
- HTML email accessibility at C$0: `lang` + `<title>` (done), alt text on logo (already), minimum 14px body (already), avoid image-only content (all key content is text), colour contrast — footer `#5B6862` on white is ~4.6:1 (AA for small text, acceptable), links underlined in footer only — body links are bold coloured; acceptable for short digest lists but underline-on-hover is not available in email; left as-is per brand.
